# DLQ for `ClickhouseProducer` — retrospective design doc

Status: retrospective — written after an initial implementation, to be revised and
used to align the code with the agreed design.

## Problem

`ClickhouseProducer.produce_arrow` inserts an Arrow batch into ClickHouse via
`clickhouse_connect`, retried up to 3 times (`_insert_with_retry`) to absorb
transient failures (network blips, brief unavailability). If all retries fail,
the exception previously propagated straight to the caller — a single
malformed or schema-incompatible row anywhere in the batch would fail the
*entire* batch, and by extension typically crash or stall the consuming node,
since a `Producer` failure has no other defined outcome.

In a Kafka → ClickHouse pipeline, batches are read from a topic and can contain
many independent events. One event with a bad value (wrong type, oversized
string, invalid encoding, a `NULL` in a non-nullable column, etc.) shouldn't be
able to:

1. Block delivery of every other, valid row in the same batch, or
2. Take down the node, which would stall consumption of all *subsequent*
   batches too, since Kafka offsets can't advance past an unprocessed batch.

We need a way to isolate and quarantine the specific row(s) causing an insert
to fail, while still delivering everything else, and without losing the
rejected data — it should be inspectable and potentially replayed later.

## Non-goals

* Retrying DLQ'd rows automatically. Once a row lands in the DLQ it's a human/
  offline concern.
* Deduplicating or rate-limiting DLQ writes.
* A DLQ for `KafkaProducer`/`KafkaConsumer` — this doc covers only
  `ClickhouseProducer`, though the mechanism is intentionally generic (see
  below) so it could extend to other producer types later.

## Solution

### Isolating bad rows: recursive bisection

`ClickhouseProducer.produce_arrow` still attempts one `_insert_with_retry` for
the whole incoming batch. If that fails (all 3 attempts exhausted) and a
`dlq_producer` is configured, it falls back to `_insert_with_dlq_fallback`,
which bisects the batch recursively:

* Batch of 1 row that fails → that row is the culprit. Wrap it as a DLQ
  record (see schema below) and send it to `dlq_producer`.
* Batch of N>1 rows that fails → split it into chunks of
  `max(1, N // split_factor)` rows and recurse on each chunk independently.

This narrows down to exactly the failing rows without needing to inspect the
ClickHouse error message, at the cost of extra insert round-trips proportional
to how deep the recursion goes. `split_factor` (default 10, configurable via
`ClickHouseOutputSettings.dlq_split_factor`) trades off round-trip count
against how large a "wasted" chunk is when one bad row poisons a chunk insert:
a higher split factor means fewer rows re-sent per recursion level but more
levels of recursion for a large batch with a single bad row.

If no `dlq_producer` is configured, a failed insert still raises after retries
are exhausted — this preserves today's fail-loud behavior for nodes that
haven't opted into a DLQ, rather than silently dropping data.

### DLQ record schema

Each rejected row is wrapped into a single-row Arrow table with a fixed
schema before being handed to `dlq_producer.produce_arrow`:

| column        | type   | contents                                                        |
|---------------|--------|------------------------------------------------------------------|
| `producer`    | string | JSON: `{"ch_url", "ch_database", "ch_table"}` — where it came from |
| `data`        | string | JSON-encoded original row                                        |
| `err_message` | string | `str(exception)` from the failed insert                          |
| `time`        | datetime (UTC) | when the row was quarantined                              |

This schema is independent of the source table's schema, so a single DLQ
sink (topic or table) can receive rejected rows from multiple source tables/
producers — `producer` is what disambiguates provenance, and `data` carries
the arbitrary original row as JSON rather than requiring a matching column
layout.

### `dlq_producer` is just a `Producer`

The DLQ target is typed as `Producer` (`tkati_core.producer.Producer`), the
same interface used for regular node outputs — not a dedicated DLQ type. In
practice this means:

* A `ClickhouseProducer` can be its own or another `ClickhouseProducer`'s
  `dlq_producer` (writing quarantined rows to a `..._dlq` table), exercised by
  `test_ch_producer_as_dlq_for_another_ch_producer`.
* A `KafkaProducer` could equally be used to push rejected rows to a DLQ
  topic instead of a table, with no changes to `ClickhouseProducer`.

`produce_arrow` calls `self._dlq_producer.flush()` once after the recursive
fallback completes (not once per DLQ'd row), so buffering producers (e.g. a
future Kafka DLQ) don't need a flush per row.

### Wiring

* `ClickHouseOutputSettings.dlq_split_factor: int = 10` — the only new setting
  surfaced to config; the DLQ *target* itself is wired by the caller passing a
  `dlq_producer` to `build_producer`/`ClickhouseProducer.__init__`, not by
  settings. There's currently no config-driven way to say "this node's output
  gets a DLQ pointed at table X" — that's assembled in application code.
* `build_producer` no longer takes a `split_factor` kwarg directly; it derives
  it from `settings.dlq_split_factor` when settings is a
  `ClickHouseOutputSettings`.

## Open questions for the revised design

* Should DLQ wiring become config-driven (e.g. an `[output.dlq]` settings
  block resolved by `build_producer`) rather than assembled by hand in
  application code?
* Is unbounded recursive bisection acceptable, or should there be a cap
  (e.g. give up and DLQ the whole remaining chunk after N levels) to bound
  worst-case round-trips against ClickHouse when many rows in a batch are bad?
* `KafkaProducer` has no DLQ fallback path today — is that in scope for this
  effort or a later one?
